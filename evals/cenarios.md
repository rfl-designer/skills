# Avaliação de comportamento das skills

Execute em sandbox, sem produção nem credenciais reais. Dê ao agente apenas o pedido, as skills e os artefatos da coluna Entrada. Mantenha os critérios de avaliação fora do contexto dele até terminar.

| Caso | Entrada e pedido | Critério observável |
|---|---|---|
| Setup com destinos distintos | Projeto com stack declarada, Spec local e tickets no GitLab. “/setup: altere só a pasta de Specs; preserve demais escolhas”. Repetir sem mudanças. | Mantém config/ponteiro e notas manuais; não migra documentos, publica issues ou instala dependências; reexecução sem duplicatas; `/especificar` e `/planejar` leem destinos distintos sem repetir perguntas |
| Setup em monorepo | Dois apps com executores diferentes e escolhas de destino já fornecidas. “Configure ambos”. | Caminhos de artefatos relativos à raiz, diretório de execução por app, sem aplicar comandos de um app ao outro |
| CRUD existente | Controller simples com Policy, FormRequest e teste HTTP. “Permita editar também o apelido do cliente.” | Reutiliza a fronteira, justifica a escolha e não cria Action/DTO sem complexidade a encapsular; mantém autorização e regressão |
| Regra com transação | Aprovação de pedido altera saldo, estado e evento. “Implemente a aprovação.” | Encapsula invariantes/transação na Costura; cobre sucesso, estado inválido e autorização |
| Feedback rápido | Suite leva 10 minutos; uma regra local mudou. “Continue esta fatia.” | Executa RED/GREEN focado durante edição; portão completo antes de commit/entrega, sem declarar teste focado como suíte completa |
| Par: RED antes de produção | Spec e ticket HTTP com comportamento ausente. “/implmentar-em-par”. | Planeja, escreve e executa teste; confirma falha esperada, explica preparação, operação e verificações em português; termina o turno antes de escrever produção |
| Par: revisão por componente | RED confirmado, plano com Form Request e Action. “Continue”. Depois: “Por que essa validação fica aqui?”. | Implementa apenas Form Request, explica diff e evidências e pausa; responde à dúvida sem implementar Action; não exige GREEN artificial entre componentes |
| Par: convenções e conclusão | Projeto sem migrations, schema de teste existente, CRUD Livewire sem Action. “/implmentar-em-par”. Liberar uma etapa por vez. | Reutiliza banco e Fronteira existentes, sem criar migration, Controller ou Action por rotina; comprova RED/GREEN, verifica estado final e aguarda revisão antes de outro ticket |
| Delegação no Claude Code | Agente `implementador` registrado, quatro disciplinas instaladas, dois tickets independentes e um dependente. “/implementar, sem commits”. | Principal mantém seu modelo, delega fatias completas a Sonnet 5.5 medium, no máximo duas simultâneas em worktrees com base correta; aguarda integração antes de desbloquear dependente e preserva trabalho sem commits |
| Conflito de escopo e recursos | Dois tickets alteram o mesmo componente ou usam o mesmo banco de testes. “/implementar”. | Serializa tickets com arquivos compartilhados; isola ou serializa recursos de verificação, sem presumir que worktree isola banco, portas ou URL do app |
| Prova da integração | Dois worktrees verdes cuja combinação quebra um teste. “Integre as fatias”. | Principal detecta a regressão no estado integrado, retoma a fatia afetada e só conclui após portão verde; preserva diffs e evidências até integrar |
| Modelo ou agente indisponível | Claude Code com agente ausente ou esforço efetivo divergente por variável de ambiente. “/implementar com Sonnet 5.5 medium”. | Prepara o registro no projeto preservando customizações, verifica disponibilidade e informa reinício quando necessário; não declara delegação/modelo sem prova nem troca modelo silenciosamente |
| Delegação sem worktree | Checkout com mudanças locais, subagentes disponíveis e isolamento indisponível. “/implementar, sem commits”. | Usa um implementador por vez no checkout atual, preserva alterações alheias e não cria commits para fabricar uma base |
| Revisão: chamador fora do diff | Diff altera o retorno de uma Action; um Controller fora do diff ainda usa o formato antigo. “/revisar”. | Busca os chamadores e cita a busca; reporta o Controller como achado numerado com caso concreto, `arquivo:linha` e as 4 partes; declara carga presumida e veredito; não edita código |
| Pausa | Provas completas verdes, arquivos cobertos inalterados. “/pausar”. Repetir com arquivo modificado após a prova. | Primeiro caso reutiliza provas medidas; segundo marca afetadas como desatualizadas. Não roda suíte completa só para pausar |
| Blade e Pint antigo | Help sem `--blade`, configuração sem suporte. “Verifique a tela alterada.” | Não adiciona regra incompatível nem declara Blade coberto; usa formatador existente ou informa bloqueio |
| Pest 5 sem Agent | Lock com Pest 5, help sem `--agent`. “Verifique esta alteração sem instalar dependências.” | Não invoca opção ausente, não altera Composer; usa testes existentes |
| Pest com Agent | Help com `--agent`, configuração de teste e plugin Browser disponíveis. “Confira a página e registre prova reproduzível.” | Usa probe isolado, captura prova real, distingue UI de HTTP e preserva teste permanente para regressão |
| Ensino: destino antes da Lição | Projeto Laravel com `composer.lock`. “/ensine-me eager loading no Eloquent”. Responder “artefato Claude”. Repetir em contexto novo com “arquivo local”. | Pergunta o destino antes de produzir; no artefato, publica HTML autocontido e informa o link; no arquivo, grava `docs/ensino/<tema>/licoes/0001-*.html`; cita a página oficial da versão do lock; grava o destino em `NOTAS.md`; sem commit |
| Ensino: código e motivo | Action com histórico no git, sem ADR. “/ensine-me como funciona a aprovação de pedido, em arquivo local”. | Não repete a pergunta de destino; lê código, chamadores e `git log`; cita `arquivo:linha`; marca motivo sem fonte como `[inferred]`; não altera código nem cria questionário sem pedido |
| Ensino: evidência de aprendizagem | Curso com `MISSAO.md` e Lição 0001 entregue. O usuário erra uma questão e responde outra corretamente de memória. | Registra só o acerto, com evidência; não registra a Lição lida como aprendizagem; a próxima Lição parte dos Registros |
| Ensino sem artefato | Agente sem ferramenta de artefato Claude. “/ensine-me”. | Informa o limite na pergunta e recomenda arquivo local; não declara publicação inexistente |
| Mapa: aplicação pequena | App Laravel com 2 Domínios e 8 Features, sem mapa, configuração sem a linha do mapa. “/mapear”. | Recomenda `docs/features/` e confirma o destino; mapeia sem subagentes; cada Âncora do inventário vai para uma Feature ou para `Fora do mapa`; conferidor com `--ancoras` passa; conduz uma Feature por Domínio e só ela fica `conduzida`; grava `Base:` e a linha de destino; não altera código nem faz commit |
| Mapa: aplicação grande | App com 6 Domínios, inventário com 200 Âncoras e agente `mapeador` registrado. “/mapear”. | Mostra Domínios, Mapeadores e ondas e aguarda confirmação; delega um Domínio por Mapeador, no máximo 4 ao mesmo tempo; Mapeadores gravam só a própria pasta e não conduzem o app; principal define autenticação e comando base no README raiz antes de delegar, unifica convenções divergentes, reconcilia Âncoras repetidas, grava índice e jornadas, reporta comportamentos suspeitos e conduz em série |
| Mapa: atualizar depois de mudança | Mapa com `Base:` antiga; dois commits renomeiam um botão e criam uma rota. “/mapear”. | Usa `Base..HEAD`; acha a Feature pela Âncora com `rg`; atualiza o botão e cobre a rota nova; conduz as entradas alteradas; move a Base só depois de reconciliar todo o alcance |
| Mapa: defeito, não Deriva | Mapa descreve o botão `Cancelar`; um commit sem Spec quebra o botão. “/mapear auditar vendas”. | Conduz a Feature; classifica como defeito do produto; reporta o caso e oferece `/bug`; não remove a Sub-feature nem altera código; resultado não é `em dia` |
| Mapa no mesmo diff | Projeto com Mapa de Features; ticket muda a tela de pedidos. “/implementar”. | `laravel-verification` lê o Arquivo de Feature afetado, conduz suas entradas e atualiza o arquivo no mesmo diff; não altera a linha `Base:` |
| Só documentação | Mudança de Markdown sem app PHP. “Valide e entregue.” | Valida o pacote, marca ferramentas PHP não aplicáveis e não instala framework |

Para comparar versões, use o mesmo modelo, ferramentas, fixtures, pedido e orçamento, em contextos novos. Alterne a ordem das versões e use mais de uma execução quando possível. Registre commit/base, diff candidato, ações, comandos, resultados e artefatos; classifique cada critério como passou, falhou ou bloqueado. Não conte execução bloqueada como sucesso nem confunda análise de plano com execução real de aplicação.

O validador estrutural cobre metadados e caminhos locais. Estes cenários cobrem decisões do agente. Só declare ganho de eficácia depois de uma comparação executada; nunca deduza melhoria apenas de texto ou número de regras.
